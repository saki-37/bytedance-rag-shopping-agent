整理时间：2026-05-20 20:00 CST  
注意：官方文档中包含共享模型 API Key，本笔记不记录密钥；原始 `docx/pdf` 仅保留本地，不同步远程。

## 一句话判断

这不是单纯做一个 RAG Chatbot，而是做一个「原生移动端 App + 后端 RAG 服务 + 商品卡片流式交互 + 可解释可靠推荐」的端到端工程项目。

最适合作为职业探索样本的点：

- 验证自己是否愿意做 `AI 应用 / RAG / Agent 工程 / 全栈交付`。
- 可以把重点放在「有限数据下的可靠推荐、反幻觉、复杂约束理解、评价闭环」上，而不是只拼模型效果。
- 和之前想做的知识注入、心理健康/行动伙伴类 AI 产品有方法论关联：都是把外部知识、用户意图和安全可靠输出连接起来。

## 课题真实要求

### 必做最小闭环

客户端：

- iOS 或 Android 原生 App，二选一即可。
- 对话窗口，支持发送文字。
- 接收并渲染 AI 流式回复。
- 回复中包含可点击商品卡片，支持跳转落地页或模拟详情页。

后端：

- Python / Go / Node.js 任选。
- 集成向量数据库。
- 实现 RAG 基本链路。
- 提供流式 API，SSE 或 WebSocket 均可。

模型能力：

- 理解模糊需求，例如「推荐护肤品」。
- 从库内商品中检索。
- 给出合理推荐理由。
- 不编造不存在的商品、价格、优惠和功能。

数据：

- 50-100 条脱敏电商数据即可。
- 字段至少包含商品名、类目、价格、详情描述、主图 URL。
- 数据量不是核心，覆盖场景和属性质量更重要。

### 明确不能踩的线

- 不能用纯 Web / H5 方案替代原生 App。
- Demo 不能需要大量手动配置。
- 不能出现明显幻觉，尤其是编造商品、价格、优惠券、库存、功能。
- 可以用 AI 开发，但答辩时必须能解释架构、链路和关键代码细节。

## 评分权重

| 维度 | 权重 | 对应策略 |
| --- | ---: | --- |
| 基础功能完整性 | 35% | 先做通端到端：原生 App -> 后端检索 -> 模型生成 -> 流式返回 -> 商品卡片 |
| 工程质量 | 25% | 清晰目录、接口设计、错误处理、依赖说明、README、技术文档 |
| 效果与可靠性 | 20% | 检索准确、少幻觉、多轮/复杂约束可用、UI 无明显 Bug |
| 加分项深度 | 20% | 不摊大饼，选 1-2 个方向做深 |

结论：先保证「可跑、可讲、可解释」，再做加分项。评审明显更看重完整工程闭环，而不是堆很多半成品能力。

## 场景层级拆解

### 基础场景：必须覆盖

- 单轮模糊推荐：如「推荐一款适合油皮的洗面奶」。
- 条件筛选：如「200 元以下的蓝牙耳机有哪些？」。

需要展示：

- 意图识别。
- 商品属性匹配。
- 参数抽取和范围过滤。
- 推荐理由来自商品资料，而不是模型自由发挥。

### 进阶场景：建议作为主打

- 多轮追问与细化：用户先说「帮我推荐跑鞋」，后续补充轻量、预算等条件。
- 主动澄清：信息不足时询问用户更看重什么。
- 对比决策：对 2-3 个商品做结构化对比，并给出推荐理由。

这部分最适合你，因为它既是 Agent 能力，也是产品体验能力，还能和「辅助决策」这个课题核心贴合。

### 高级场景：谨慎选 1 个做深

可选方向：

- 反选 / 排除约束：如「不要含酒精」「除了耐克还有什么」。
- 购物车与下单：对话式 CRUD，展示购物车状态变化。
- 拍照找货：图像理解 + 相似商品检索。
- 端侧体验优化：骨架屏、卡片动效、首 Token 延迟优化。

当前建议：优先做「多轮上下文 + 反选/排除 + 多商品对比」这一组。它最贴合 RAG 可靠性，也最容易在三周内形成清晰答辩叙事。拍照找货可以作为 stretch goal，不要一开始就把它设为主线。

## 推荐项目定位

建议把 Demo 场景收窄为一个垂直品类，而不是泛电商。

优先候选：`敏感肌/油皮/户外场景的护肤与防晒导购`

原因：

- 属性结构丰富：肤质、成分、功效、价格、使用场景、禁忌成分。
- 很适合展示反选能力：不要酒精、不要香精、孕期慎用、预算限制等。
- 很适合做多轮澄清：肤质、预算、场景、是否敏感肌、是否需要补妆等。
- 数据 50-100 条可以做得足够精，而不需要大规模真实电商库存。
- 和你本来关心的「女性友好、身心健康、降低决策负担」有轻连接，但仍符合电商商业化题面。

一句话产品叙事：

> 面向有具体肤质、预算和成分禁忌的用户，提供一个能追问、能排除、能对比、能解释依据的护肤/防晒智能导购 Agent。

## 技术路线初稿

### 客户端

建议选 Android / Kotlin：

- 你已经有 Kotlin 和安卓权限经验。
- 题目只要求 iOS/Android 二选一。
- Android 原生比重新上 Swift/iOS 更稳。

关键模块：

- Chat UI：消息流、用户输入、流式回复。
- 商品卡片：商品名、价格、主图、关键标签、推荐理由、详情跳转。
- 状态展示：加载中、检索中、生成中、错误重试。
- 可选：购物车状态或收藏状态。

### 后端

建议选 Python / FastAPI：

- 上手快，适合三周内交付。
- SSE 实现流式接口比较直接。
- RAG、评测、数据脚本生态成熟。

建议目录：

```text
client/   Android 原生 App
server/   FastAPI + RAG + 模型调用
data/     商品数据与构建脚本
docs/     架构设计、评测方案、Demo 脚本
```

### RAG 链路

最小链路：

1. 商品数据标准化：商品名、类目、价格、描述、成分/属性、适用场景、禁忌条件、主图 URL。
2. Chunking：按商品粒度为主，必要时把「成分/功效/评价」拆成子块。
3. 向量检索：Chroma / Qdrant / pgvector 均可，优先选本地简单方案。
4. 规则过滤：价格、类目、否定条件先做结构化过滤。
5. Prompt 生成：只允许基于检索结果回答，缺信息时必须说不确定或反问。
6. 结构化输出：文本推荐 + 商品卡片 JSON。
7. 流式返回：先返回解释文本，再推送商品卡片或一起返回结构化事件。

## 三周推进建议

### 第 1 阶段：2-3 天内打通最小闭环

目标：

- Android App 能发文本。
- FastAPI 能接收问题。
- 后端能检索 20-50 条商品数据。
- 模型能返回推荐理由。
- App 能显示流式回复和商品卡片。

判断标准：可以录一个 1 分钟端到端 Demo。

### 第 2 阶段：一周内做出主打能力

目标：

- 扩展到 50-100 条商品数据。
- 支持多轮上下文。
- 支持预算、肤质、场景、禁忌成分等条件。
- 支持「不要某成分/某品牌」的反选。
- 支持 2-3 个商品对比。

判断标准：可以稳定跑 8-12 个典型 Case。

### 第 3 阶段：最后一周打磨和答辩

目标：

- 做评测集：检索准确率、回答是否编造、复杂约束是否命中。
- 补 README、架构文档、Demo 脚本。
- 打磨 UI：商品卡片、加载状态、错误提示、少量动效。
- 准备 3-5 分钟演示视频或讲解脚本。

## 今晚/明天讲解会优先确认的问题

1. 原生 App 是否允许只提供 Android 模拟器 Demo？是否必须真机？
2. 商品详情页/购物车/下单是否可以使用 mock 数据与模拟流程？
3. 数据可以自采、合成或手工整理吗？是否需要来源说明？
4. 多模态是强要求还是加分项？如果做文字主线 + 图片输入 stretch 是否可接受？
5. Embedding / VLM 不提供 Key 的情况下，是否允许使用其他模型或本地模型？
6. 评分时更看重「多模态拍照找货」还是「RAG 可靠性 + 多轮复杂约束」？
7. 提交仓库是否必须公开？如果使用共享 API Key，提交前如何处理配置和密钥？
8. Demo 需要现场运行，还是可以提交录屏 + 可运行代码？

## 当前决策建议

第一志愿确定为 RAG 多模态电商智能导购是合理的。

但执行时不要把题目理解成「我要做一个全品类电商助手」。更稳的定义是：

> 做一个垂直护肤/防晒导购 Agent，用原生 Android + FastAPI + RAG 跑通端到端闭环，并把多轮澄清、反选约束、商品对比和反幻觉做成主打能力。

如果后续讲解会明确要求必须强多模态，再把「拍照找货」调整为第二主线；否则它只作为加分项，不抢 MVP 的工期。
