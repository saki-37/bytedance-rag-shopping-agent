# 最终提交演示视频脚本

目标：录制 5-10 分钟带讲解视频，覆盖端到端链路、客户端 App、后端服务、普通文字导购、流式返回、商品卡片、详情页、RAG/防幻觉技术解释，以及稳定时的多模态或语音能力。

建议主版时长：6-8 分钟。平台或评委要求更短时，可使用本文末尾 3-5 分钟精简版结构。

## 录制前准备

| 项目 | 要求 |
| --- | --- |
| 后端 | `uvicorn app.main:app --host 0.0.0.0 --port 8000` 已启动 |
| Provider | `/health` 显示 `mock_llm=false`，正式口径为 `llm_provider=ark` |
| Android | 最新 Debug App 已安装，执行过 `adb reverse tcp:8000 tcp:8000` |
| 数据 | 已运行 `python scripts/build_index.py` |
| Query | 预先跑通文字导购、信息不足追问、商品详情 |
| 可选能力 | 图片、ASR、TTS 至少人工验证一次；不稳定则不放主视频现场演示 |
| 安全 | 录屏不展示真实 API Key、`.env`、私人图片、手机号、地址 |

## 5-10 分钟主版

| 时间段 | 操作画面 | 建议讲解词 | 展示评分点 | 风险与备用方案 |
| --- | --- | --- | --- | --- |
| 0:00-0:35 | 仓库 README / 终端 health / Android 首页 | “这是一个原生 Android + FastAPI 的 RAG 智能导购，不是 H5。后端 health 可以看到当前使用真实 provider，客户端通过 SSE 接收流式回复。” | 基础完整性、工程质量 | 终端不要露 Key；如果 provider 名称敏感，只展示字段不展示环境变量 |
| 0:35-1:40 | App 输入 `我是油皮，想要200元以内通勤防晒` | “用户需求里的预算、肤质和通勤场景会先进入检索约束。首屏会先出现临时气泡，完整 Planner 和检索完成后再返回商品卡片和正式回答。” | 文字导购、RAG、流式返回、quick_reply | 模型慢时等待，不要手动连点；可剪掉等待空白 |
| 1:40-2:30 | 展示商品卡片，点击详情页 | “商品卡片里的品牌、标题、价格、图片和详情字段都来自本地商品库，不由模型自由编。详情页展示适合人群、使用场景、卖点和注意事项。” | 商品卡片、详情页、数据证据 | 如果图片不加载，改用已验证截图插入讲解 |
| 2:30-3:20 | 点击左上角侧边栏图标新建会话，输入 `我想买护肤品，你推荐什么？` | “信息不足时系统不会为了凑推荐强行推商品，而是先追问肤质、预算或功效。这是减少乱推和幻觉的第一道防线。” | 复杂场景、主动澄清、可靠性；顺带展示本地会话抽屉 | 如果历史污染，用左上角侧边栏新建会话再演示 |
| 3:20-4:20 | 输入敏感肌/排除条件 query | “对于敏感肌、不要酒精、不要刺激这类风险条件，系统会把排除项带入检索和生成。资料没有明确支持的地方，会表达资料未说明，而不是说绝对安全。” | guardrail、防幻觉、边界表达 | 如果真实模型表达太满，解释 guardrail/fallback 并展示文档/报告 |
| 4:20-5:20 | 在防晒推荐后问 `第一款和第三款怎么选？` | “Android 会把上一轮商品 ID 带回后端，后端用 conversation state 解析‘第一款/第三款’，再用商品证据生成对比，而不是让模型猜上一轮商品。” | 多轮对话、商品指代、对比决策 | 表格换行不佳时只讲核心字段 |
| 5:20-6:10 | 输入 `我去三亚玩，想从防晒到穿搭配一套` 或展示 Planner 文档 | “复杂场景由 Planner 拆成 scene_bundle 和 search_slots，检索层按计划跨类目选品。这比单轮推荐更接近真实导购方案。” | 加分项深度、场景化 Planner | 真实调用慢时展示 `docs/30_scene_bundle_planner_implementation.md` 和已验证结果 |
| 6:10-7:10 | 可选：上传商品/包装图片 | “图片输入已经接入：Android 上传图片，后端生成 image_plan，再把可见品类、品牌、包装文字等线索拼进现有 RAG。当前是 text-first 图片理解，不是图搜图。” | 多模态加分 | VLM 未配置时跳过现场，只展示接口和边界 |
| 7:10-8:00 | 可选：语音输入或 TTS 播报 | “语音输入走本地 ASR sidecar，TTS 用 Android 系统播报，目标是让移动端体验更完整。它们是可选增强，不影响文字 RAG 主链路。” | 交互创新、可访问性 | sidecar/系统 TTS 不稳时只展示设置入口 |
| 8:00-8:50 | 展示设计文档架构图 | “核心不是让模型自由聊天，而是 Android -> FastAPI -> Planner -> RAG -> LLM -> guardrail -> SSE。价格、图片和商品事实来自数据，模型负责组织表达。” | 工程质量、架构可解释 | 不要讲太散，聚焦 3 亮点 |
| 8:50-9:30 | 展示 claim audit 或可靠性表 | “我们不说零幻觉，而是把高风险主张拆成商品事实，发现、拦截、修复或兜底。库存、优惠、下单等红线会被后端拦截。” | 效果与可靠性、减分项规避 | 如果时间不足，这段压到 20 秒口播 |
| 9:30-10:00 | 总结和边界 | “最终亮点是证据约束 RAG、场景化 Planner 多轮对比、原生移动端多模态/语音体验。当前不做真实下单、库存、优惠，也不把 mock 结果当真实效果。” | 提交定位、边界清晰 | 避免说全品类/全自动/零幻觉 |

补充（可选、不占主时长）：App 左上角侧边栏图标可打开会话抽屉（新建/切换本地会话），顶部“演示身份”文字可切换本地 user_id（默认 `local-demo-user`），用于展示常用对象/记忆按用户隔离。讲解口径务必说“演示级本地身份”，不要说成真实登录或账号系统。

## 推荐讲解主线

1. 先证明能跑：App + 后端 + health + SSE。
2. 再证明有产品体验：商品卡片、详情页、流式输出。
3. 再证明不是普通 chatbot：RAG、metadata filter、evidence-bound prompt、guardrail。
4. 最后讲加分项：Planner 场景化、多轮对比、图片/语音/TTS。

## 3-5 分钟精简版

| 时间段 | 操作画面 | 解说重点 |
| --- | --- | --- |
| 0:00-0:25 | health + Android 首页 | 原生 Android + FastAPI，真实 provider，不是 H5 |
| 0:25-1:30 | 文字防晒 query | 预算/肤质/场景进入 RAG，SSE 流式返回 |
| 1:30-2:05 | 商品卡片 + 详情页 | 商品事实来自数据源，不由模型编 |

| 3:35-4:25 | 可选图片/语音/TTS 一项 | 移动端交互加分，口径保守 |
| 4:25-5:00 | 架构图 + 3 亮点总结 | 证据约束 RAG、Planner 多轮、原生多模态/语音；不做库存/优惠/下单 |

## 最终检查

- 视频时长在 5-10 分钟之间，或另备 3-5 分钟精简版。
- 能看到 Android App 和后端服务，不只有幻灯片。
- 至少展示一次流式回答、商品卡片和详情页。
- 至少口头说明商品/价格/优惠幻觉如何规避。
- 多模态/语音只在稳定时现场展示，不稳定时作为已接入能力与边界说明。
- 视频中没有真实 Key、私人图片、手机号、地址、未脱敏 `.env`。
