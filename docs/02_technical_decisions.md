# 技术决策记录

用于记录字节 AI 全栈挑战赛项目中的关键技术选择、取舍原因和后续影响。每条决策尽量保留当时的上下文，方便之后复盘，也方便答辩时解释「为什么这样做」。

## ADR-001：客户端主线选择 Android Kotlin 原生

日期：2026-05-21  
状态：已确定

### 背景

课题要求交付 iOS 或 Android 原生 App，不接受纯 Web / H5 方案。当前项目只需要在一个移动端平台上完成端到端 Demo，因此跨端复用不是首要目标。

可选方案包括：

- Android Kotlin 原生。
- iOS Swift 原生。
- React Native。
- Flutter。

### 决策

客户端主线选择 **Android Kotlin 原生**，优先使用 Jetpack Compose 构建界面。

本项目不把 React Native / Flutter 作为主线方案，也不选择 Swift 作为主线方案。

### 原因

1. **更符合题面和评审语境**
   - 官方文档明确强调 iOS / Android 原生 App。
   - Android Kotlin 是最容易被解释为「原生客户端工程」的方案。
   - React Native 虽然有 native 能力，但在比赛语境里容易被视为跨端框架，存在额外解释成本。

2. **项目只需单平台交付**
   - React Native 的主要优势是跨端复用，但本课题不要求 iOS 和 Android 同时交付。
   - 为了一个平台引入跨端框架，不一定节省时间，反而会增加依赖、打包和调试复杂度。

3. **设备与调试条件更现实**
   - 当前没有 iPhone 真机，Swift / iOS 真机交互调试不方便。
   - Android 有真机和模拟器两种路径，遇到输入、交互、网络等问题时更容易排查。

4. **已有 Kotlin / Android 经验可复用**
   - 之前做过 Android/Kotlin 项目，虽然曾遇到无障碍权限、后台持续运行等复杂问题，但这些不是本课题 MVP 的核心。
   - 本项目第一阶段只需要聊天输入、流式展示、商品卡片和网络请求，权限复杂度可控。

### 影响

正向影响：

- 技术栈更贴合官方要求，降低评审风险。
- 客户端能力可以集中在聊天体验、流式渲染、商品卡片和状态反馈上。
- 后续答辩时更容易解释工程取舍。

代价：

- 暂时放弃跨端复用。
- 需要处理 Android 工程、Gradle、模拟器/真机网络连接等客户端工程问题。

### 风险控制

- MVP 阶段不做无障碍权限、后台常驻等高复杂权限。
- 多模态如图片输入若后续进入范围，优先使用系统图片选择器，减少直接摄像头权限和设备差异。
- Demo 优先保证 Android Emulator 可运行，再补真机验证。
- 后端本地调试时，Android Emulator 访问宿主机服务使用 `10.0.2.2`。

### 后续待定

- 是否采用 Jetpack Compose 作为唯一 UI 方案。
- 多模态输入是否进入第一版范围。
- Demo 最终使用模拟器、真机，还是两者都准备。

## ADR-002：保留原始数据，新增结构化增强层

日期：2026-05-21  
状态：已确定

### 背景

主办方提供的数据集由 AI 生成，允许参赛者补充字段、标注属性和扩充数据。当前数据集结构规整，但很多关键导购信息仍然藏在自然语言里，例如肤质、材质、使用场景、禁忌条件、适合人群、用户踩雷点等。

如果直接覆盖原始 JSON，后续会难以区分：

- 哪些是官方给的原始素材。
- 哪些是我们自己补充的结构化判断。
- 哪些字段用于检索、过滤、评测或商品卡片展示。

### 决策

保留官方原始数据不直接改动，后续新增一个结构化增强层。

可能形式：

- `normalized_products.jsonl`
- `enriched_products.json`
- 或按类目生成 `data_enriched/`

增强层中记录从原始文本抽取或人工补充的字段，例如肤质、功效、成分、材质、使用场景、排除条件、适合/不适合人群等。

### 原因

1. **可追溯**
   - 能区分官方原始数据和我们自己的加工判断。
   - 答辩时可以解释数据治理流程，而不是只展示结果。

2. **方便迭代**
   - 如果结构化字段设计需要调整，可以重建增强层，不污染原始数据。
   - 后续可以做人工标注、AI 辅助标注、脚本校验三种方式的对比。

3. **利于 RAG 和评测**
   - 原始文本适合做向量检索。
   - 增强字段适合做硬过滤、反选约束、商品卡片展示和 golden case 评测。

### 影响

正向影响：

- 数据管线更清晰。
- 后端可以同时读取原始文本和结构化字段。
- 评测时能明确判断模型是否基于已知字段回答。

代价：

- 需要额外设计 schema。
- 需要写一次数据转换/增强脚本。
- 前后端接口需要决定哪些字段暴露给客户端商品卡片。

### 后续待定

- 增强层最终文件格式。
- 第一批人工标注样例数量。
- 是否扩充美妆护肤类目到 50 条左右。
